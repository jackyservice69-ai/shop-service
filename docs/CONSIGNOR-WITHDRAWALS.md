# ถอนรายได้ฝากขาย (local / schema 16)

ตัวแทนที่ได้รับอนุมัติแจ้งถอนจากแผง “ถอนรายได้ฝากขาย” ใน `/consignment` ระบุยอด ธนาคาร เลขบัญชี และชื่อบัญชี ขั้นต่ำ 1 บาท สูงสุดตามรายได้ฝากขายที่ยังถอนได้ในกระเป๋า ยอดเติมเงินและค่าคอมมิชชั่นแนะนำเพื่อนไม่เพิ่มสิทธิ์ถอน

## ยอดและสถานะ

- รายได้ฝากขายเกิดจากออร์เดอร์สำเร็จและชำระครบตามกติกาเดิม ไม่มีรายได้จากออร์เดอร์ที่ยังรอสำเร็จ
- คำนวณส่วนที่ถอนได้จาก immutable ledger ตามลำดับรายการ จ่ายซื้อสินค้าจากยอดอื่นก่อน หากใช้รายได้ฝากขายไปแล้ว ยอดที่ถอนได้ลดตามจริง การเติมเงินภายหลังไม่ทำให้รายได้ที่ใช้ไปกลับมาถอนได้
- การคืนเงินออร์เดอร์เดิมคืนสิทธิ์เฉพาะส่วนของรายได้ฝากขายที่เคยใช้จ่ายในออร์เดอร์นั้น ไม่แปลงยอดเติมเงินเป็นรายได้ถอน
- ส่งคำขอ: `pending` พร้อม ledger `withdrawal_hold` ติดลบทันที ยอดนั้นไม่สามารถใช้ซื้อสินค้าหรือขอถอนอีกได้
- อนุมัติ: `approved` ยังคงกันยอด ไม่หักเงินซ้ำ
- ผู้มีสิทธิ์รับดำเนินการ: `processing` จองคำขอให้ผู้ดำเนินการเพียงคนเดียวก่อนโอนผ่านธนาคาร ผู้รับดำเนินการเท่านั้นบันทึกโอนได้
- ปิดหน้าต่างระหว่างโอนแล้วกลับมาทำต่อที่ตัวกรอง “กำลังดำเนินการโอน” ได้ ผู้รับดำเนินการหรือเจ้าของร้านคืนคิวเป็น approved ได้เมื่อยืนยันตรวจสอบแล้วว่ายังไม่โอน พร้อมเหตุผล การคืนคิวไม่คืนยอดกระเป๋า
- หลังโอนจริงสำเร็จ: กรอกเลขอ้างอิงแล้วบันทึก `paid` ยอดไม่หักซ้ำ เลขอ้างอิงไม่ซ้ำแบบไม่แยกพิมพ์ใหญ่เล็ก
- ตัวแทนยกเลิกได้เฉพาะ pending; ผู้อนุมัติปฏิเสธ pending/approved พร้อมเหตุผล คืนยอดด้วย `withdrawal_release` ครั้งเดียว ขณะ processing ต้องยืนยันไม่มีการโอนและคืนคิวก่อนปฏิเสธ

ระบบนี้ไม่เรียก API โอนเงินธนาคาร การอนุมัติและรับดำเนินการยังไม่ได้โอนเงินจริง เจ้าหน้าที่ต้องโอนเองแล้วบันทึกผล การจองคิวและเลขอ้างอิงช่วยควบคุมขั้นตอนในเว็บ ไม่รับรองธุรกรรมที่เจ้าหน้าที่ทำภายนอกเว็บ

## สิทธิ์

หลังบ้าน `/admin/withdrawals`:

| สิทธิ์ | ความสามารถ | สิทธิ์ที่ต้องมีร่วม |
|---|---|---|
| `withdrawals` | ดูรายการ คำขอ และบัญชีรับเงิน | finance |
| `withdrawals_approve` | อนุมัติ / ปฏิเสธ | withdrawals |
| `withdrawals_pay` | รับดำเนินการ คืนคิวของตน บันทึกโอน | withdrawals |

เจ้าของร้านใช้ได้ด้วยสิทธิ์เดิม ยังไม่เพิ่มสิทธิ์ใหม่ให้บทบาทพนักงานอัตโนมัติ เจ้าของกำหนดในเมนูสิทธิ์การใช้งานได้ ผู้ดูอย่างเดียวไม่ดำเนินการได้ และทุกคนรวมเจ้าของไม่สามารถอนุมัติหรือดำเนินการถอนของตนเอง

กระดิ่งส่งให้ตัวแทนตามสถานะ ส่งคิว pending เฉพาะผู้มีสิทธิ์อนุมัติ และส่งคิว approved เฉพาะผู้มีสิทธิ์โอน เมื่อมีการรับ/ตัดสินใจคิวเก่าถูก resolve ใช้สิทธิ์ปัจจุบันเสมอ

## การเงินและความปลอดภัย

เงินหน่วยสตางค์ integer, ตรวจ request body บนเซิร์ฟเวอร์, session/CSRF/Origin เดิม, version ทุก transition, idempotency key สำหรับส่งคำขอ, atomic transaction รวม ledger/status/audit/notifications, ห้ามแก้บัญชีรับเงินหรือยอดหลังส่งแล้ว และห้ามแก้/ลบรายการสิ้นสุด

Ledger กันยอด/คืนยอดแสดงในประวัติกระเป๋าและหน้าธุรกรรมตามสิทธิ์ finance รายการ paid และเลขอ้างอิงตรวจในคำขอถอน ไม่เพิ่ม expenses อัตโนมัติเพราะเป็นการจ่ายหนี้รายได้ตัวแทนที่เกิดขึ้นแล้ว ไม่ควรนับค่าใช้จ่ายซ้ำ

## Migration และการตรวจ

Schema 16 เพิ่ม withdrawals และขยายเงื่อนไข notifications โดยย้าย parent/child พร้อมกัน รักษา notification/read IDs, wallet, ledger และ audit เดิม Startup production สำรอง SQLite และตรวจ integrity ก่อน migration ตามกลไกเดิม ยังไม่ได้เปิดฐานข้อมูลจริงหรือ deploy ในงานนี้

API tests: สิทธิ์ แหล่งรายได้/การคืนเงิน กันยอด การทำซ้ำ คำขอชนกัน การจ่ายซ้ำ สิทธิ์ตนเอง บัญชีถูกระงับ การจองคิวสองเจ้าหน้าที่ rollback และ migration/reopen/backup ใช้ fixture แยกทั้งหมด

Browser test: ซื้อสินค้าตัวแทนใน fixture จนสำเร็จ จากนั้นส่งคำขอผ่าน UI อนุมัติ รับคิว บันทึกโอน ยกเลิก ตรวจมือถือ 390 px/desktop 1440 px และ Axe ไม่มีธุรกรรมจริง
